# Фронтенд GisOrders — дизайн

Дата: 2026-10-28
Статус: на согласовании

## 1. Зачем

У GisOrders есть готовый бэкенд: заказы на работы с деревьями, отклики исполнителей, чаты в реальном времени, загрузка фото, JWT-авторизация. Фронтенда нет — только однофайловый прототип `test.html`, который не развивается и не годится в продакшен.

Нужен настоящий клиент: мобильный в первую очередь, устанавливаемый на телефон, с картой, поиском заказов рядом с пользователем и живым чатом. Один аккаунт совмещает обе роли — заказчика и исполнителя — и переключается между ними одним движением.

## 2. Цели

- Закрыть полный путь заказчика: зарегистрироваться → создать заказ с фото и точкой на карте → получить отклики → выбрать исполнителя → обсудить детали в чате → закрыть заказ.
- Закрыть полный путь исполнителя: найти заказы рядом → отфильтровать → откликнуться с ценой и сообщением → договориться в чате → получить заказ.
- Дать переключение ролей внутри одного аккаунта без выхода и повторного входа.
- Хорошо работать на телефоне 360 px и на десктопе; устанавливаться как PWA.
- Выглядеть как продукт, а не как форма ввода: зелёная тема, спокойные поверхности, аккуратные карточки.

Успех: человек с телефона проходит путь «нашёл заказ → откликнулся → договорился в чате», не встречая непонятных экранов и не теряя введённые данные.

## 3. Не-цели

- Админ-панель. В API нет списка пользователей, панель потребует доработки бэкенда.
- Восстановление пароля («забыли пароль»). Требует почты или SMS и новых эндпоинтов.
- Отзывы, рейтинги, избранное, push-уведомления.
- Офлайн-работа и синхронизация очереди действий.
- Нативные приложения в сторах.
- Тёмная тема в первой версии.

## 4. Анти-цели

- Копировать `test.html` один в один. Прототип — источник знаний об API, не образец интерфейса.
- Зашивать в код ключи карт и чужие токены. В прототипе лежит ключ Яндекс-тайлов, в новом клиенте его не будет.
- Делать «универсальный» интерфейс, который одинаково неудобен и на телефоне, и на десктопе.
- Прятать бизнес-ограничения (лимит откликов, нельзя откликнуться на свой заказ) в невнятные ошибки.

## 5. Ограничения и факты о бэкенде

Всё ниже проверено по коду, а не по предположениям.

- API: префикс `/api/v1`, JSON, Bearer-токен. CORS открыт (`*`), credentialed-запросы не используются.
- Токены: access 15 минут, refresh 30 дней с ротацией. `POST /users/refresh`, `POST /users/logout` (отзывает refresh), `POST /users/me/password` (меняет пароль и отзывает все сессии).
- Регистрация: email, username, телефон (необязателен, формат `+7XXXXXXXXXX`), пароль ≥ 8 символов, обязательно заглавная буква и цифра.
- Заказы: `open` / `assigned` / `closed`. Отклики: `pending` / `accepted` / `rejected`.
- `/orders/available` требует `user_lat`, `user_lon`, `radius_km`; исключает свои заказы, заказы с истёкшим дедлайном и те, куда пользователь уже откликался. Поддерживает `min_price`, `max_price`, `tree_type`, `max_height`, `sort_by` (`created_at` / `deadline` / `min_price`), `sort_order`, пагинацию.
- **Поиска по тексту в API нет.** Его нужно добавить (см. раздел 9).
- Отклик создаётся вместе с чатом. При принятии отклика заказ становится `assigned`, остальные отклики отклоняются, их чаты закрываются.
- Лимит откликов: 3 в сутки (настраивается на бэкенде).
- Расстояние до заказа API не возвращает — считаем на клиенте по `lat`/`lon` пользователя и заказа.
- У заказчика нет эндпоинта «все отклики по всем моим заказам»: только `GET /orders/{id}/proposals`. Экран откликов придётся собирать из своих заказов.
- Чаты: `GET /chats` отдаёт `last_message` и `unread_count`; `GET /chats/{id}` — сообщения. Realtime: `WS /api/v1/ws/chats/{chat_id}`, первый кадр `{"type":"auth","token":"..."}`, события `message.created`, `message.read`, `typing`.
- Загрузка изображений: `POST /uploads/images`, multipart `file`, ответ `{"url": ...}`; фото передаются в заказе как массив строк.
- Медиа раздаются с `/media`.

## 6. Подходы

Рассматривались три.

**A. React + Vite + TypeScript — SPA.** TanStack Query, React Router, Tailwind, Leaflet, WebSocket-обёртка, PWA. Отдельная сборка, раздаётся nginx, `/api` проксируется на FastAPI.
Плюс: зрелая экосистема, много готовых решений для карты, форм и тестов. Минус: больше кода, чем в Svelte.

**B. Vue 3 + Vite + TypeScript.** Технически равноценно: Pinia, Vue Router, те же библиотеки. Осмысленно, если сопровождать будет человек, знающий Vue. Минус: примеров и готовых компонентов под наши задачи меньше.

**C. Next.js.** SSR для приложения, закрытого логином, не даёт ничего, зато добавляет Node-процесс в прод. Отклонён.

**Выбран A.** Причины: бэкенду нужен только статический фронтенд и прокси; Leaflet не требует ключа и позволяет сменить провайдера тайлов на Яндекс или 2ГИС одной строкой; PWA даёт установку на телефон без сторов.

## 7. Архитектура

### 7.1 Каталог

```
frontend/
  index.html
  package.json
  vite.config.ts
  tsconfig.json
  Dockerfile
  nginx.conf
  public/            # иконки, манифест
  src/
    app/             # провайдеры, роутер, глобальные стили
    api/             # клиент, типы, запросы по доменам
    entities/        # order, proposal, chat, user: типы + отображение
    features/        # поиск, фильтры, отклик, создание заказа, смена роли
    pages/           # экраны
    widgets/         # шапка, нижняя навигация, карта, карточка заказа
    shared/          # ui-кит, утилиты, конфиг
```

Правило зависимостей: `pages → widgets → features → entities → api/shared`. Обратные импорты запрещены.

### 7.2 Стек

- React 19, TypeScript (strict), Vite.
- TanStack Query — серверное состояние, кэш, повторные запросы, инвалидация.
- React Router (data router) — маршруты и загрузка данных.
- Zustand — только сессия и режим роли; всё остальное живёт в Query или URL.
- Tailwind с CSS-переменными дизайн-токенов; без сторонних UI-китов, чтобы не тащить чужой вид.
- react-hook-form + zod — формы; схемы повторяют ограничения бэкенда.
- Leaflet + react-leaflet + markercluster, тайлы OpenStreetMap.
- date-fns с локалью `ru`.
- vite-plugin-pwa — манифест, иконки, service worker для статики.

### 7.3 API-клиент

Тонкая обёртка над `fetch`:

- базовый URL из `VITE_API_BASE_URL`, по умолчанию `/api/v1`;
- подставляет access-токен;
- на `401` один раз обновляет пару токенов и повторяет запрос; параллельные запросы ждут общий промис обновления, а не дёргают refresh по очереди;
- если refresh не удался — чистит сессию и уводит на `/login` с запоминанием адреса возврата;
- приводит ошибки бэкенда к общему виду `{ code, message, status }` и сохраняет русский `message` из ответа;
- таймаут 15 секунд, отмена через `AbortController` при уходе с экрана.

Типы API пишутся руками по схемам бэкенда (OpenAPI-генератор не берём: одна лишняя зависимость и шумные типы).

### 7.4 Авторизация

- access-токен — только в памяти (Zustand), refresh — в `localStorage`.
- Компромисс осознанный: refresh в `localStorage` уязвим к XSS, но API отдаёт токены в теле ответа и не умеет httpOnly-cookie. Смягчаем: строгий CSP, никакого `dangerouslySetInnerHTML`, экранирование пользовательского текста.
- Обновление токена координируется между вкладками: блокировка `navigator.locks` (запасной вариант — `BroadcastChannel`), refresh выполняет только одна вкладка, остальные ждут результат. Бэкенд считает повторное использование refresh-токена компрометацией и отзывает все сессии — без координации две открытые вкладки разлогинили бы пользователя везде.
- Старт приложения: есть refresh → `POST /users/refresh` → `GET /users/me`. Пока идёт проверка, показываем скелетон, а не форму входа (иначе мигание).
- Выход: `POST /users/logout` с refresh, затем очистка.
- Смена пароля: после успеха все сессии отозваны — показываем «Войдите заново» и уводим на вход.

### 7.5 Режим роли

- Хранится в `localStorage` (`gisorders.mode`: `customer` | `executor`), по умолчанию `customer`.
- Это не права, а представление: бэкенд роли не знает, любой пользователь может и заказывать, и откликаться.
- Влияет на подписи вкладок, заголовки экранов, содержимое «Мои заказы» / «Мои работы» и стартовые фильтры ленты.
- Переключатель — в шапке: сегмент из двух состояний. На телефоне компактный, с инициалами при нехватке места.
- Переключение не сбрасывает фильтры и не перезагружает страницу.

### 7.6 Realtime

- Один WebSocket на открытый чат, закрывается при уходе с экрана.
- Первый кадр — авторизация токеном; при истечении access переподключаемся после обновления токена.
- Переподключение с экспоненциальной задержкой (1 → 30 с) и джиттером; при возврате сети — сразу.
- После переподключения сообщения перезапрашиваются, чтобы не потерять пропущенное.
- Индикатор «нет связи» в шапке чата; поле ввода остаётся активным, отправка ставится в очередь до восстановления (одно сообщение, без полноценного офлайна).

### 7.7 Карта

- Leaflet, растровые тайлы OSM, без ключей. Провайдер вынесен в конфиг одной строкой.
- Кластеризация маркеров при большом числе заказов.
- Выбор карточки в ленте центрирует карту на маркере и открывает подпись с ценой.
- Полноэкранная карта — отдельный маршрут `/map`, с теми же фильтрами и кнопкой «Назад к списку».
- Если геолокация запрещена: показываем выбор точки на карте и запоминаем её. Блокируется только лента и карта — профиль, чаты, заказы и переход по прямой ссылке работают; вместо ленты показывается экран «Укажите, где искать» с выбором точки. Блокировать весь интерфейс из-за координат нельзя: человек без геолокации должен иметь доступ к переписке.

### 7.8 Фото

- До 5 фото на заказ, каждое до 5 МБ (ограничение бэкенда).
- Превью показывается сразу, загрузка идёт параллельно; при ошибке — повтор для конкретного файла.
- Сжатие на клиенте до 1920 px по длинной стороне перед отправкой (бэкенд всё равно ужимает, но экономим трафик на мобильной сети).

## 8. Экраны

### 8.1 Вход и регистрация

Email + пароль. Ошибки — под полями, серверные (`rate_limited`) — общей плашкой с таймером. Регистрация: email, имя, телефон (необязателен), пароль с индикатором требований (8 символов, заглавная, цифра) — требования показываются заранее, а не после отказа. После входа — туда, откуда пришли, иначе на ленту.

### 8.2 Лента (главная)

Мобильная версия — список: поисковая строка, чипы активных фильтров, карточки заказов. Карта — кнопкой в строке фильтров, открывается полноэкранно.
Десктоп — сплит: список слева, карта справа, фильтры над списком.
Карточка: название, расстояние, срок, порода и высота, число откликов, цена, статус.
Прокрутка бесконечная по `page`, по 20 штук.
Пустое состояние: «В радиусе N км заказов нет» + кнопки «Увеличить радиус» и «Сбросить фильтры».
Потянуть вниз — обновить (на телефоне).

### 8.3 Фильтры

Панель снизу на телефоне, поповер на десктопе. Состав: где искать (геолокация или точка на карте), радиус 1–50 км, цена от и до, порода дерева (фиксированный список + «Любая»), высота (любая / до 10 м / до 20 м), сортировка (новые, по сроку, по цене).
Кнопка показывает живой счётчик найденного: «Показать 12».
Активные фильтры видны чипами над списком и снимаются одним нажатием.
Состояние фильтров и поиска — в URL, чтобы ссылку можно было переслать и обновить страницу без потери настроек.

### 8.4 Карточка заказа

Фото-галерея, название, описание, адрес, срок, вилка цены, порода, высота, диаметр, статус, дата публикации, мини-карта с точкой.

Режим исполнителя: кнопка «Откликнуться» → форма с ценой и сообщением. Если уже откликался — показываем свой отклик и статус. Если заказ свой — форма недоступна с пояснением. Если лимит исчерпан — понятное сообщение с временем сброса.

Режим заказчика (свой заказ): список откликов с ценой, сообщением и статусом; «Принять» с подтверждением («Остальные отклики будут отклонены, чаты закроются»). После принятия — переход в чат. «Закрыть заказ» и «Редактировать» доступны, пока заказ открыт.

### 8.5 Создание и редактирование заказа

Поля: название, описание, вилка цены, срок, адрес, порода, высота, диаметр, фото, точка на карте.
Порода выбирается из справочника с подсказками, но допускает своё значение (см. 9.3).
Точка ставится кликом по карте; адрес вводится текстом и не геокодируется в первой версии (геокодер требует ключа) — подсказка «поставьте точку на карте, адрес увидит исполнитель».
Валидация на клиенте повторяет бэкенд: название ≥ 5, описание ≥ 10, срок в будущем, цены не противоречат друг другу.
Черновик сохраняется в `localStorage`, чтобы не потерять введённое при случайном закрытии.
При редактировании занятого заказа поля блокируются с пояснением.

### 8.6 Мои заказы

Режим заказчика — `GET /orders/my`, группы по статусам: открытые, в работе, закрытые. У каждой карточки счётчик откликов.
Режим исполнителя («Мои работы») — принятые отклики и их заказы; отдельная группа «Завершённые».

### 8.7 Отклики

Режим исполнителя — `GET /orders/proposals/my`: цена, заказ, статус, дата. Принятые ведут в чат, ожидающие можно отозвать.
Режим заказчика — список своих открытых заказов с числом откликов (`proposals_count` из списка заказов); подробности откликов подгружаются при раскрытии заказа. Так мы обходим отсутствие общего эндпоинта и не делаем N+1 запросов на старте.

### 8.8 Чаты

Список: аватар-заглушка, имя собеседника, последнее сообщение, время, бейдж непрочитанных. Сортировка по времени последнего сообщения.
Чат: сообщения с группировкой по времени, разделители дат, свои — справа зелёным, чужие — слева белым. Отправка по Enter (Shift+Enter — перенос), на телефоне — кнопка. Индикатор «печатает», отметка прочтения, статус соединения. Прокрутка вниз при новом сообщении, если пользователь уже внизу.
Заголовок чата ведёт в заказ.

### 8.9 Профиль

Имя, email, телефон. Редактирование имени/телефона. Смена пароля. Переключатель ролей (дублирует шапку, с пояснением). Выход. Удаление аккаунта — с подтверждением вводом слова «удалить».

Дату регистрации не показываем: в модели `User` нет `created_at`, а добавлять поле в базу ради одной строки в профиле — лишняя миграция.

## 9. Поиск, счётчики и доработки бэкенда

### 9.1 Поиск по тексту

Поиск согласован как часть первой версии, но в API его нет. Требуется изменение бэкенда:

- в `OrderFilters` добавить `search: Optional[str] = Field(None, max_length=200)`;
- в роутере `/orders/available` — query-параметр `search`;
- в `OrderService.get_available_orders` — при непустом значении фильтр `ILIKE` по `title` и `description` с экранированием `%`, `_` и `\`;
- миграция не нужна; для объёма данных первой версии достаточно `ILIKE`, полнотекстовый индекс — позже.

Фронтенд: строка поиска над лентой, debounce 350 мс, значение в URL (`q`), при пустом результате — «По запросу ничего не найдено» и кнопка сброса.

Правка входит в эту же итерацию и деплоится вместе с фронтендом. Важно: FastAPI молча игнорирует неизвестные query-параметры, поэтому на старом бэкенде поиск вернул бы **неотфильтрованную** ленту как результат запроса. Чтобы это не выстрелило, строка поиска закрыта флагом сборки `VITE_FEATURE_SEARCH` и включается только после выката бэкенда.

### 9.2 Счётчики откликов и найденного

Макеты показывают «3 отклика» на карточке, «12 заказов · 5 км» в шапке ленты и «Показать 12» на кнопке фильтров. Сейчас API этого не отдаёт: `OrderResponse` не содержит числа откликов, а `/orders/available` возвращает список без общего количества. Добавляем:

- `OrderResponse.proposals_count: int` — число откликов в статусе `pending`. Считается коррелированным подзапросом в списковых запросах (`/orders/available`, `/orders/my`, `/orders/{id}`), чтобы не порождать N+1. Отклонённые и принятый отклик в счётчик не входят: после выбора исполнителя карточка честно показывает «Исполнитель выбран», а не «1 отклик».
- `X-Total-Count` в ответе `/orders/available` — общее число заказов под текущими фильтрами, без учёта пагинации. Заголовок, а не поле в теле: ответ остаётся списком, контракт не ломается.
- В `CORSMiddleware` добавить `expose_headers=["X-Total-Count"]` — иначе браузер не покажет заголовок фронтенду при кросс-доменной разработке.

Фронтенд: карточка показывает «3 отклика» (или «новый» при нуле), шапка ленты — «12 заказов · 5 км», кнопка фильтров — «Показать 12». Если заголовка нет, интерфейс деградирует до «Показать» без числа, а не ломается.

Тесты на бэкенде: корректность `proposals_count` при `pending`, `accepted` и `rejected`; наличие и точность `X-Total-Count` при фильтрах и пагинации.

### 9.3 Порода дерева

Поле `tree_type` в базе — свободный текст. Строгий справочник сделал бы фильтр точным, но запретил бы редкие породы — лиственницу, ольху, черёмуху. Поэтому:

- в форме — комбобокс: подсказки из справочника (сосна, ель, берёза, дуб, липа, клён, тополь, осина, ольха, ива, лиственница, ясень, вяз, кедр, пихта, яблоня, вишня, слива, груша, черёмуха, рябина), но ввести своё значение не запрещено;
- бэкенд нормализует `tree_type` при создании и обновлении заказа: обрезка пробелов, нижний регистр, `ё` → `е`, схлопывание повторных пробелов;
- фильтр по породе сравнивает нормализованные значения, а не сырой текст;
- существующие записи приводятся к тому же виду одноразовым скриптом (не структурной миграцией).

### 9.4 Что не меняем

Тип работ (спил, обрезка, уборка) не добавляем: такого поля в модели заказа нет, это отдельная задача с миграцией и изменением формы.

## 11. Состояния и ошибки

- Загрузка: скелетоны повторяют форму контента, без вращающихся кругов на весь экран.
- Ошибка сети: плашка «Нет соединения» + кнопка «Повторить», контент остаётся на экране, если он уже был.
- Ошибки API переводятся по `code`: `daily_proposal_limit`, `order_not_open`, `rate_limited`, `forbidden`. Неизвестные — общий текст плюс `message` от сервера.
- Оптимистичные обновления: отправка сообщения, принятие отклика (с откатом при ошибке).
- Все формы сохраняют введённое при ошибке.

## 12. Адаптивность и PWA

- Точки перелома: до 640 — телефон, 640–1024 — планшет, от 1024 — десктоп со сплитом.
- Нижняя навигация — только на телефоне; на десктопе вкладки в шапке.
- PWA: манифест, иконки, `display: standalone`, тема `#2F6B45`. Service worker кэширует оболочку и статику; API-запросы не кэшируются, чтобы не показывать устаревшие заказы.
- `viewport-fit=cover`, отступы под «челку» и жестовую полосу.

## 13. Доступность

- Контраст текста ≥ 4.5:1; зелёный на белом проверен.
- Все поля с `label`, ошибки связаны через `aria-describedby`.
- Тосты и ошибки — `aria-live="polite"`.
- Управление только с клавиатуры: фокус-ловушка в модалках, закрытие по Esc.
- `prefers-reduced-motion` отключает анимации переходов.
- Иконки без текста имеют `aria-label`.

## 14. Тестирование

- Юнит: расчёт расстояния, форматирование даты и цены, разбор ошибок API, сборка query-строки фильтров.
- Компоненты (Vitest + Testing Library): карточка заказа, панель фильтров, форма отклика, список чатов.
- E2E (Playwright) на трёх сценариях: вход → лента → отклик → чат; создание заказа с фото; принятие отклика и закрытие заказа.
- MSW для подмены API в тестах; отдельный набор фикстур под статусы.
- Ручная проверка: 360 px, 768 px, 1440 px; клавиатура; отключённая геолокация; медленная сеть.

## 15. Сборка и деплой

- `frontend/Dockerfile`: multi-stage — `node:22-alpine` собирает, `nginx:alpine` раздаёт. Итоговый образ без node.
- `nginx.conf`: SPA-fallback на `index.html`, прокси `/api/` и `/media/` на `backend:8000`, gzip, кэш статики с хешами, CSP.
- В `docker-compose.prod.yml` добавляется сервис `frontend` на порту 8080, зависит от `backend`.
- Прод обязан работать по HTTPS: без secure context не устанавливается PWA и не запрашивается геолокация. TLS терминируется перед фронтендом (внешний прокси или домен с сертификатом); в конфигурации nginx предполагаем, что `X-Forwarded-Proto` приходит снаружи.
- Переменные: `VITE_API_BASE_URL` (по умолчанию `/api/v1`), `VITE_WS_URL` (по умолчанию от текущего хоста).
- Разработка: `vite dev` с прокси на `http://127.0.0.1:8000`, бэкенд и Postgres — через текущий `docker-compose.yml`.
